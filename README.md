# OC Fate Loom · 命运织机

这是我把多年前的 OC Fate Generator 拆开重做后的版本。

它现在不替你写故事。你先给两名角色分别选下目标、立场、边界、弱点和选择，再决定这段关系最后要付什么代价；页面会把命中当前规则的地方画出来。没有命中规则的线不会出现，没想好的部分也可以留空。

在线使用：[yuqing-cai.github.io/oc-fate-loom](https://yuqing-cai.github.io/oc-fate-loom/)

> 当前版本只做离线结构检查，不调用模型，也不会向访客索取 API Key。草稿默认不保存。

## 怎么用

从“境遇”开始，挑一件两个人共同躲不开的事。接着分别替她和他作选择，再决定两人的权力关系、相处方式、代价和结局。十七条轴不用一次填完。

选到几项后，可以打开“命运图”：

- **因果**表示按当前规则，前一项给后一项提供了来处；
- **支持**表示两项能互相托住，但前者并没有造成后者；
- **张力**可以继续写，不等于选错；
- **冲突**表示按当前定义，两项不能同时成立；
- **开放**把答案留给后面的场景或作者。

“开放结构”允许带着缺口查看；“闭合命运”更严格，所有已经启动的路径都要走通，阻断冲突也要先处理。填满表格本身不算闭合。

## 这版先不做什么

站点提供模型的默认体验、以及访客使用自己 API Key 的方式，都只留了界面和代码边界，目前没有启用。供应商、模型、转发服务和生产安全限制尚未确定，我不想先拿一个过时接口把空位填上。

未来两条路线即使启用，也会分开处理凭据、端点和传输方式。当前设计草案见 [`docs/api-boundaries.md`](docs/api-boundaries.md)；尚未完成的安全条件见 [`docs/security.md`](docs/security.md)。

## 本地开发

要求 Node.js `^20.19.0` 或 `>=22.12.0`，并使用 pnpm 10。

```bash
pnpm install --frozen-lockfile
pnpm dev
```

完整检查：

```bash
pnpm check
```

## 代码放在哪里

```text
src/
├── domain/   # 轴、选项、规则、命运图与闭合判定
├── app/      # 页面状态、草稿、离线检查与配置导出
├── api/      # 尚未启用的默认路线 / BYOK 边界
├── ui/       # DOM 与命运图组件
├── main.ts   # 页面组装
└── styles.css
```

规则为什么这样分，见 [`docs/content-model.md`](docs/content-model.md)。

## 草稿与隐私

离线结构检查不会调用模型或第三方服务。草稿默认关闭；主动开启后，浏览器会保存语言、路线、输出模式、选择、备注、供应商／模型 ID 和种子。备注只在草稿开启时留在浏览器中，但导出时始终会写入文件。

未来若启用 BYOK，只有专用 Key 输入框会使用瞬时内存：它不得进入应用状态、草稿或导出文件。备注是普通自由文本，可能留在草稿里，也会进入导出文件，所以不要把 Key 粘贴进去。
